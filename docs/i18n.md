# i18n 語系維護

QJudge 使用 `react-i18next`，目前支援繁體中文（`zh-TW`）、英文（`en`）、日文（`ja`）與韓文（`ko`）。繁體中文是新增介面文案與公開文件時的第一份內容來源；其他語言要在內容穩定後翻譯，不用複製繁中內容假裝已完成。

## 兩種不同的內容

介面文案位於 `frontend/src/i18n/locales/<language>/`。每個 JSON 檔是一個 namespace，例如 `common.json`、`contest.json`、`admin.json` 與 `chatbot.json`。

公開 Markdown 位於 `frontend/public/docs/<language>/`。文件導覽結構由 `frontend/public/docs/config.json` 決定，導覽名稱則放在各語言的 `docs.json`。

這兩者使用不同的檢查工具，不要把 Markdown 翻譯問題當成一般 i18n key 問題處理。

## 修改介面文案

先在 `frontend/src/i18n/locales/zh-TW/` 的正確 namespace 新增或修改 key。命名要描述用途，不把完整中文句子當成 key。

使用變數時採用 i18next 格式：

```json
{
  "welcome": "{{name}}，歡迎回來"
}
```

在元件中明確選擇 namespace：

```tsx
const { t } = useTranslation("common");

return <h1>{t("welcome", { name: user.name })}</h1>;
```

完成翻譯後，在 frontend container 執行同步檢查：

```bash
.codex/skills/qjudge-env-compose-owner/scripts/qjudge-dc.sh dev \
  exec -T frontend npm run check:i18n
```

`npm run sync:i18n` 會改寫多個語言檔案。只有在準備一起檢查並提交這些變更時才執行，不要用它來產生假的翻譯。

## 修改公開文件

新增可出現在導覽的頁面時，需要同時確認：

1. Markdown 檔名與 `config.json` 中的 slug 相同。
2. `docs.json` 包含 section 與 item 的導覽名稱。
3. Markdown 內的相對連結可以解析。
4. 文件頁能完成 build。

檢查公開文件覆蓋狀態：

```bash
.codex/skills/qjudge-env-compose-owner/scripts/qjudge-dc.sh dev \
  exec -T frontend npm run check:docs
```

這個指令會列出缺少的 Markdown 與導覽 key，但目前以警告方式結束。若某批內容明確採分階段發布，例如先完成繁中部署指南，警告可以暫時存在；工作說明必須清楚記錄尚未翻譯的語言。

最後建置文件頁：

```bash
.codex/skills/qjudge-env-compose-owner/scripts/qjudge-dc.sh dev \
  exec -T frontend npm run build:docs
```

## 撰寫原則

- 使用台灣常用詞彙與標點。
- 同一個功能在不同語言中保持相同限制、權限與安全警告。
- JSON key 維持既有排序方式，避免只為重排產生大型 diff。
- 不翻譯程式變數、API path、檔名與 command name。
- 文件內容變動後重新檢查連結與 build，不只檢查 JSON key。
