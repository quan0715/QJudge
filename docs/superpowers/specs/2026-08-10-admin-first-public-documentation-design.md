# QJudge 管理者優先公開文件設計

## 目標

重新設計 QJudge 公開文件的入門路徑，讓校園教師、課程助教與開課單位能從一套尚未設定的 QJudge，依序完成平台交接、教師資格、教室、學生名冊與第一場考試的準備。

文件不以功能清單或服務架構開場，而是說明一門正式課程為何需要這些設定、每一步由誰負責，以及完成後會替下一步建立什麼條件。

## 敘事來源與產品定位

文件敘事依論文前三章的研究問題、場域與需求推導整理，但不把論文正文直接搬進操作指南。

QJudge 的公開定位為：一套開源、可自行部署，供正式課程與考試使用的系統。其主要場景是學生實體到場，以自備裝置和一般瀏覽器應試。系統保存身分、名冊、考卷、作答、監考事件、證據與批改紀錄；違規判斷、評分規準與正式分數仍由教師及助教決定。

入門文件應建立以下認知：

- 登入成功只代表系統知道使用者是誰，不代表已取得教師資格、課堂成員資格或應試資格。
- 管理員負責平台層級的帳號與教師資格，不參與單一課堂的日常教學工作。
- 教師以教室保存一學期共用的成員關係，再在教室下建立多場考試。
- AI 協助出題、整理 rubric 或提出評分建議，但屬於既有工作中的選用步驟；正式寫入仍由人確認。

## 讀者與角色交接

主要讀者是第一次負責導入 QJudge 的系統管理者或開課單位。文件在「管理教師資格」後明確交接角色：

1. 管理員完成部署、第一個管理員帳號與教師資格設定。
2. 管理員登出。
3. 後續以教師帳號建立教室、學生名冊與考試。

超級使用者不作為日常教學帳號。教師完成資格開通後，教室與考試截圖均使用教師帳號。

## 第一階段範圍

第一階段從平台介紹開始，結束於教師完成第一場考試的發布前檢查。

### 1. 平台概覽

說明 QJudge 面對的教學問題、正式考試場景、角色責任與完整考試生命週期。讀者應先知道平台解決什麼問題，再閱讀操作步驟。

本頁不列出 Docker、PostgreSQL、Redis 等服務清單。技術元件移至部署或維護文件。

### 2. 開始使用

作為閱讀路徑首頁，依讀者目前狀態分流：

- 自行架設者先閱讀「架設與部署」。
- 已有可用站台者從「建立管理員帳號」開始。
- 已取得教師帳號者從「建立教室」開始。

本頁不再教學生提交程式，也不混入個人化設定、SSE 或 AI service 等技術資訊。

### 3. 架設與部署

沿用已完成的最小部署、object storage、選用功能與故障排除四頁。入門路徑只說明何時需要閱讀，不重複部署指令。

### 4. 建立管理員帳號

說明第一個 superuser 的用途，以 production Compose 指令建立帳號，再登入 QJudge 確認管理入口可用。

指令使用文字 code block；截圖呈現登入後的實際管理介面，不以終端機截圖代替可複製指令。

### 5. 管理教師資格

主流程使用管理員的「使用者管理」畫面：找到已完成註冊的帳號，將角色由學生改為教師，再確認角色已更新。

教師啟用連結保留為補充方式，適合教師尚未完成帳號準備，或管理者希望讓受邀者自行完成開通時使用。兩條路不在主流程並列，避免第一次使用者無法判斷應選哪一種。

### 6. 建立教室

切換到教師帳號。說明教室代表一門課，保存學期內共用的教師、助教、學生與考試。使用一致的課程名稱、代碼與描述建立示範教室，並確認教室首頁已出現。

### 7. 管理學生名冊

說明平台帳號、正式修課名冊與教室成員資格的差異。教師依名冊核對學生使用的 QJudge 帳號，再加入教室並檢查人數與角色。

本階段只說明目前系統真實提供的加入方式。未與校務系統或 LMS 自動同步的流程，不寫成既有功能。

### 8. 準備考試

在示範教室下建立第一場考試，涵蓋名稱、時程、考試類型、配分、題目與評分規準。至少準備一題客觀題與一題問答題，讓讀者理解自動判分與人工批改的差異。

AI 協助出題或整理 rubric 放在相對應步驟中，以「選用」標示。沒有 AI provider 時，教師仍能完整走完相同流程。

### 9. 確認考試內容

從教師角度預覽考卷，核對學生名冊、時程、題目順序、配分、rubric 與監考設定。頁面明確列出發布前檢查清單，並說明首筆正式作答後題目內容將受到限制。

第一階段以「考試已具備發布條件」作為完成標準，不進入學生應試畫面。

## 延後範圍

下列內容另行設計與撰寫，不在第一階段順帶加入：

- 學生登入、加入教室、考前檢查、正式作答、交卷與查看作答報告。
- 教師與助教的即時監考、暫停、鎖定、解除、重新開放與事後證據查核。
- 人工批改、AI 建議分數覆核、正式分數確認、成績發布與疑義處理。
- 平台管理員的特殊維運、資料修復與例外處理。
- AI 模型 registry、自訂 endpoint 與模型擴充。
- 英文、日文與韓文翻譯。

## 導覽與舊文件整併

公開導覽採流程優先：

1. `overview`：平台概覽。
2. `quick-start`：開始使用與閱讀分流。
3. 現有 deployment section：自行架設者的條件式分支。
4. 新的管理者至教師準備流程：建立管理員帳號、管理教師資格、建立教室、管理學生名冊、準備考試、確認考試內容。

既有 `admin-overview`、`teacher-overview`、`teacher-first-class-setup` 與 `create-exam` 的有效內容須遷入新流程；完成遷移後，從公開導覽移除重複入口。若舊 slug 已有外部連結，實作時先確認文件站是否支援 redirect；不支援時保留一頁簡短導向，避免留下兩份會分別過期的正文。

現有學生、監考、批改與進階參考文件暫時保留，但不插入第一階段的線性「下一步」。

## 章節標題與語氣

標題使用短而明確的名詞或動作，不使用口號，也不過度口語化。建議標題如下：

- 平台概覽
- 開始使用
- 建立管理員帳號
- 管理教師資格
- 建立教室
- 管理學生名冊
- 準備考試
- 確認考試內容

正文站在第一次導入正式課程的讀者角度，先說明本步驟解決的問題，再提供操作。避免假設讀者理解 role、classroom、roster、rubric、object storage 或 MCP；名詞第一次出現時用一句話說明即可，不在操作指南展開內部架構。

每頁採固定節奏：

1. 這一步要完成什麼。
2. 開始前需要具備什麼。
3. 依實際畫面完成操作。
4. 如何判斷已成功。
5. 常見錯誤或權限邊界。
6. 下一步。

## 示範資料

截圖與操作說明使用專用的虛構資料，不使用真實學生、課程或正式考試紀錄。

建議情境：

- 課程：`115 學年度作業系統`
- 課程代碼：`CS-OS-115`
- 教師：`王老師`
- 助教：`陳助教`
- 學生：使用數名不對應真實人物的中文姓名與 `example.test` email
- 考試：`第一次段考`
- 題目：一題作業系統單選題與一題問答題

示範資料應能從管理員授權教師一路沿用至教室與考試，避免不同頁面出現互不相關的帳號與課程名稱。登入密碼、token、真實 domain、object storage credential 與其他秘密不得出現在畫面中。

## 真實系統截圖

所有操作圖均取自當前本機 QJudge，不使用 mockup、舊版示意圖或 AI 生成介面。

截圖規則：

- 使用固定桌面 viewport，保留 QJudge 的頁面標題、主要導覽與操作脈絡；不保留瀏覽器網址列、桌面或其他應用程式。
- 以 PNG 保存文字清晰度，集中放在 `frontend/public/docs/images/admin-getting-started/`。
- 檔名描述畫面與步驟，例如 `teacher-role-updated.png`、`classroom-created.png`。
- 每張圖附具體 alt text 與圖說，說明讀者要看哪個狀態，不重複畫面上所有文字。
- 操作入口與完成結果分開截圖；只有畫面足以同時證明兩者時才共用一張。
- 不在圖片中燒錄箭頭、編號或大段說明。操作重點由正文與圖說指出，以免介面小幅變動後整張圖失效。
- 截圖前先檢查姓名、email、token、邀請碼、時間與其他可能識別資料。

建立管理員帳號使用可複製的 Compose command；完成後以實際登入畫面證明帳號可用。其餘頁面由瀏覽器依文件步驟操作並截圖，確保文字描述與目前介面一致。

## 驗證方式

實作完成後至少執行：

- 公開文件路徑與本機連結檢查。
- `npm run check:docs`，確認繁中導覽 key 與 Markdown 檔案一致；其他語系缺頁依既定延後範圍回報。
- `npm run build:docs`。
- 逐張檢查圖片可讀性、裁切、alt text 與敏感資料。
- 以管理員與教師帳號重新走一次線性閱讀路徑，確認每一步都能在目前系統完成。
- 搜尋舊日期、分支、PR、過時健康檢查、錯誤角色敘述與重複入口。

文件只能描述實際完成驗證的操作。若介面缺少文件需要的入口，先記錄差距，再決定調整產品或縮小文件主張，不以文字補出不存在的功能。
